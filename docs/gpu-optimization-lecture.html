An engineering lecture · HocusFocus star-detection optimization

Chasing the Slow Steps

How a CUDA card sped up an already-optimized astrophotography pipeline — and why the biggest win turned out to be an algorithm the GPU merely exposed. What was considered, what was tried, what was rejected, and what any similar effort should measure first.

Prologue

A pipeline that had already been optimized three times

The subject is HocusFocus, a NINA plugin whose Star Detection Optimization wizard re-runs a star detector thousands of times over a saved auto-focus sweep, searching a twelve-dimensional parameter space. Before this work began, the optimizer had already been made 10–13× faster by an early/late pipeline split with context caching, its wavelet had been rewritten with SIMD, and its evaluation budget had been tuned. The project's own documents concluded — twice, with measurements — that the remaining hot code was memory-bandwidth bound, and named that as the argument against a CUDA port.

Then an RTX 5060 Ti arrived in the development machine, with a workflow insight attached: an optimization run is a saved folder of FITS files. It can be carried to whatever machine has the GPU. Deployment to end-user rigs — the historical objection — stopped mattering.

The question worth a lecture is not "did the GPU help." It is why the prior negative conclusion and the eventual 2–3× speedup are both correct, and how to tell which regime you are in before writing a kernel.

Part 1 · Measure the fraction you can touch

The number that decides everything is not in the profiler

The optimizer alternates two kinds of evaluation. A fast step reuses a cached "early context" and re-runs only cheap per-star gating — tens of milliseconds. A slow step rebuilds that context: hotpixel filtering, Gaussian convolutions, an à-trous wavelet, noise estimation, histogram statistics — seconds per frame at 61 MP. Project folklore said the cache achieved "99% reuse," which sounds like the slow steps barely exist.

That number counts detections. Counting seconds tells the opposite story: a slow step costs 30–70× a fast one, so even a 9–24% rebuild rate put the slow steps at 60–93% of wall-clock on real runs. The first act of the project was re-measuring exactly this — the "early fraction" f — per dataset, because the ceiling of any acceleration is 1/(1−f) and no kernel can beat arithmetic.

A stale table almost killed the project. The last published stage breakdown predated the SIMD wavelet rewrite and showed the wavelet at 44% of a detection. Re-profiling showed it at ~9% — the true dominant cost had moved to a single-threaded histogram scan. Every optimization effort inherits numbers like this. Re-measure before believing them.

Part 2 · The option space

Choosing a GPU stack is mostly choosing your failure modes

Four routes were considered for a C#/.NET 8 WPF plugin:

Rejected

OpenCV CUDA build (OpenCvSharp)

The pipeline already spoke OpenCV, but no official CUDA runtime package exists for OpenCvSharp; community builds were stale and gigabytes large, and custom native builds are exactly the deployment nightmare a plugin cannot carry.

Rejected

OpenCL via UMat / T-API

Lowest-effort on paper, but it only offloads the OpenCV calls — the custom wavelet and statistics stay on CPU — and it falls back silently, which makes performance claims unverifiable.

Fallback

ComputeSharp (DirectX 12)

Vendor-neutral and toolkit-free, held in reserve. Its cost: no fp64 guarantee, which the exactness strategy below leans on. It remains the designated route if AMD/Intel support is ever wanted.

Chosen

ILGPU 1.5.3 (CUDA backend)

Pure managed NuGet package that JIT-compiles C# kernels to PTX through the display driver — no CUDA toolkit, one DLL to ship. One sharp edge found by testing, not reading: RTX 50-series (SM_120) requires ≥1.5.3, and its LibDevice-backed transcendentals are broken on Blackwell — this pipeline needs only add/mul/min/max/sqrt/floor, all PTX-native, so the constraint cost nothing.

The stack sanity check paid for itself in an hour: saxpy showed 12.7M "mismatches" that turned out to be ptxas fusing multiply-add into FMA — a single-rounding difference that matches MathF.FusedMultiplyAdd exactly. That one observation defined the entire divergence budget of everything that followed.

Part 3 · Equivalence by construction

You cannot be bit-identical. Decide what you can be.

The project has a strict discipline: detection changes must be bit-identical or ship behind a version bump. GPU float arithmetic cannot be bit-identical to CPU arithmetic — summation order and FMA contraction see to that. The move that made the port trustworthy was classifying every stage by what kind of math it is:

Exactly reproducible: order statistics and integer arithmetic. The 3×3 median is a sorting network; the 65,536-bin histogram buckets by (int)floor(v·65536) in double; the local background grids are per-block medians selected by an exact radix-select on float bit patterns. These produce the same bits on any hardware.

Tolerance-class: convolutions and reductions — the Gaussians, the wavelet, the K-σ moments. These were written to replicate the CPU's semantics bug-for-bug (the same border reflection, the same tap order, the same InRange epsilon quirks, fp64 accumulators) so the residue is pure FMA noise, ~1e-7 relative.

Then the decisive measurement: does that noise ever cross a decision boundary? Across every test frame, the binarized structure map — the surface every downstream decision reads — showed zero flipped pixels. And because "never" is not provable, the residual risk is fenced structurally: the GPU flag participates in the detector's cache keys, so a GPU-built result can never be silently reused as a CPU one, and the final landed settings are CPU-evaluated by construction.

Part 4 · The ledger

What was tried, and what the measurements said

Every entry below was measured, not argued. The null results matter as much as the wins — two of them are the proof of where the bottleneck actually lives.

Kept

The full early chain on GPU — 16.7× at 61 MP

Hotpixel median, Gaussians, wavelet, K-σ, histogram: 3,573 ms of CPU work became 214 ms including transfers. Individual stages ran 19–75× faster; the GPU's ~448 GB/s memory bandwidth against ~90 GB/s of system DRAM is exactly the ratio the old "bandwidth-bound" analysis said CPU SIMD could never buy.

Kept

Local-background grids by exact radix-select — 68×

First implemented as "leave the grids on CPU"; they promptly became 54% of the GPU chain. Selecting the k-th element by MSB-first radix over order-preserving float bits made them exact and fast — the only stage where the exactness requirement and the performance answer were the same idea.

Rejected

Pinned staging buffers

On this PCIe Gen3 host, page-locked transfers measured 7.2 GB/s against 7.0 pageable — the staging memcpy bought nothing. Direct span copies from the OpenCV Mat's memory were simpler and faster. On a Gen4/5 host this trade likely reverses; measure yours.

Null result

Chain v2 (−40%) and a deeper GPU pool

Per-chain CUDA streams cut the isolated chain from 301 to 214 ms; doubling the pooled working sets attacked queueing. End-to-end wall moved by approximately zero, twice. This is the most valuable pair of measurements in the project: the bottleneck had moved off the GPU entirely, and no amount of further kernel work could matter.

Kept

Run-index candidate collection — bit-identical 5.7×

The sequential "flood-fill" the GPU could not absorb turned out to spend its time raster-scanning 61M background pixels, not walking stars. A parallel run-length index feeding a literal translation of the legacy walker — same seeds, same growth, same point order — kept bit-identity (proven against the retained legacy code as an oracle) while cutting the stage from 810 to 141 ms.

Adopted as default

True connected components — the accidental quality win

Studying why the walker resisted parallelization exposed that it wasn't computing connected components at all: its bounding-box zeroing erased real stars that overlapped an earlier candidate's box. An 8-connected union-find collector, offered as an opt-in toggle, landed a higher optimizer objective on every dataset tested — on the one human-labeled run, J went 0.856→0.920, a gain ~50× larger than anything the tuning work had ever argued over. It shipped as the new default behind a detector version bump. The GPU project's biggest win used no GPU.

Kept

Caching the debayer instead of accelerating it

Bayered frames re-ran a ~1.2 s CFA-filter + debayer on every rebuild. A GPU debayer was considered and skipped: the recompute is parameter-keyed and usually redundant, so a prepared-source cache keyed on (frame, hotpixel params) removed it exactly — byte-identical, helping CPU and GPU arms alike. Deleting work beats accelerating it.

Rejected

GPU work outside optimization

Autofocus, sensor modeling, and single-frame detection never touch the GPU — enforced by a params-level gate set only by the optimization wizard and harness, and guarded by a source-scan test that fails the build if a third assignment site ever appears. Scope you can prove is scope you can defend.

Part 5 · Why the gains land where they do

One clustered number, spread by arithmetic

The validation sweep ran 28 datasets — 19 real captures from the project's autofocus bank and 9 simulated rig configurations spanning ultrawide refractors to obstructed Cassegrains — each optimized twice, GPU off and on, with everything else identical.

The clean result inside that table: fast steps were identical between arms on all 28 datasets — the GPU never touches them — while the slow-step speedup clustered tightly around 2.8×. End-to-end spread (1.0× to 3.7×) is then nothing but each search's appetite for rebuilds. A run whose search converges without probing the expensive axes gets 1.0× at zero overhead; a rebuild-hungry search gets nearly the full 2.8×. The degradations map one-to-one onto the parts deliberately left on CPU: small sensors (transfer overhead), donut-dense obstructed rigs (candidate collection inflates), bayered rigs (the debayer share), and star-dense or labeled runs whose fast steps are themselves expensive.

Correctness across the sweep: ~5,900 GPU builds, zero fallbacks, zero declines; 25 of 28 datasets landed bit-identical objectives on identical search trajectories, and the three exceptions were float-noise path divergence landing equal-or-better. The GPU arm was never slower than the CPU arm on any dataset.

Conclusion

What transfers to your next acceleration project

The current approach wins because every millisecond of GPU speed is aimed at the only place the search actually spends slow time — the early rebuild — while everything the GPU is bad at (irregular per-star gating, an order-dependent scan, a vendor-locked debayer) was either left alone, deleted, or fixed as an algorithm rather than ported. In order of how much they mattered:

  1. Measure the fraction you can touch, at the granularity of the decision. Cache-hit percentages, profiler top-tens, and last year's stage tables all answered the wrong question. The ceiling was set by seconds-weighted early fraction, per dataset — one afternoon of measurement that correctly predicted every later result.
  2. "Bandwidth-bound" is an argument against wider SIMD, not against a GPU. The prior negative conclusion was locally right: more CPU instructions could not help. A device with five times the memory bandwidth is a different claim entirely — and workflow changes (carry the data to the machine) can dissolve deployment objections that once settled the question.
  3. Replicate semantics bug-for-bug, then verify decisions, not bits. Classify each stage as exactly-reproducible (order statistics, integer bucketing) or tolerance-class (convolutions), copy the reference implementation's quirks deliberately, and measure divergence where it matters: did any downstream decision flip? Zero flipped binarization pixels is a far stronger statement than any epsilon.
  4. Trust null results; they tell you when to stop. A 40% faster chain and a deeper pool that move end-to-end by nothing are not failures — they are the proof the bottleneck relocated, delivered for the price of two experiments.
  5. When an accelerator can't absorb a stage, ask why before porting harder. The sequential scan resisted the GPU because it wasn't the algorithm everyone assumed it was. The investigation produced a bit-identical 5.7× CPU rewrite and exposed a correctness bug whose fix — plain connected components — outvalued the entire GPU effort on quality. The blocker was the treasure.
  6. Make the fallback graceful and the scope provable. Off by default everywhere except the one path that wants it; a heuristic that declines small frames and missing hardware; a latch that stops retrying after repeated failures; and a source-scan test that turns "trust me, it's optimization-only" into a build guarantee.

The honest summary for the reader planning similar work: the kernels were the easy two days. The value was in the measurement discipline around them — and in being willing to let the project's best result come from a place nobody was looking.
